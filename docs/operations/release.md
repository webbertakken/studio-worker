# Releases

How a version becomes the assets users install and the auto-updater fetches.

## Pipeline

1. release-please bumps the version and changelog in a release PR; merging it does not tag.
2. A maintainer pushes `studio-worker-v<X.Y.Z>` (see `AGENTS.md`, *Releasing*).
3. The tag runs [`release.yml`](../../.github/workflows/release.yml), generated by cargo-dist:

| Job | Does |
| --- | --- |
| `plan` | `dist host --steps=create`: the build matrix and the release notes |
| `build-local-artifacts` | one archive per target (cargo-dist's CPU build) |
| `custom-build-cuda` | the CUDA archive for x86_64 Linux ([`build-cuda.yml`](../../.github/workflows/build-cuda.yml)) |
| `build-global-artifacts` | the shell + PowerShell installers, `sha256.sum`, `source.tar.gz`; then the hand-written step below |
| `host` | creates the GitHub Release with every `artifacts-*` file at once |

Every asset lands in one `gh release create`, so a release is never visible without its CUDA
archive or its installer checksums.

## Assets

| Asset | What |
| --- | --- |
| `studio-worker-<target>.tar.xz` / `.zip` | cargo-dist's build for each of the five targets |
| `studio-worker-x86_64-unknown-linux-gnu-cuda.tar.xz` | the CUDA variant (below) |
| `<archive>.sha256` | the archive's sha256, `<hex> *<name>` |
| `studio-worker-installer.sh` / `.ps1` | the installers; the shell one chooses the variant |
| `studio-worker-installer.{sh,ps1}.sha256` | what the auto-updater verifies an installer against |
| `sha256.sum` | every archive's sha256, the CUDA one included |
| `dist-manifest.json`, `source.tar.gz` | cargo-dist's manifest and the source |

## CUDA variant

The in-process LLM (llama.cpp via `llama-cpp-2`) runs on the CPU in cargo-dist's build. The CUDA
variant is the same binary built with `--features cuda`, so every layer is offloaded to an NVIDIA
GPU.

### What it is

- **Target**: x86_64 Linux only, the target where the in-process LLM is built and NVIDIA GPUs are
  common. Windows has no in-process LLM (`llama-cpp-2` does not link with MSVC, see
  `Cargo.toml`; its LLM is the provisioned Vulkan `llama-cli`), macOS has no NVIDIA GPUs, and
  aarch64 Linux CUDA hosts (Jetson, Grace) are rare.
- **Toolkit**: CUDA 12.9, the newest 12.x. Built on `ubuntu-22.04`, like cargo-dist's x86_64 Linux
  build, so both need the same glibc (2.35).
- **Runtime needs only the NVIDIA driver**: cudart and cuBLAS are linked statically; the binary's
  only CUDA dependency is `libcuda.so.1`, which the driver installs. Without it the binary does
  not start, hence the installer's driver check. With the driver but no usable GPU, llama.cpp
  finds no CUDA device and the LLM runs on the CPU.
- **Minimum driver**: 525.60.13 (CUDA 12 minor-version compatibility) for the GPUs listed below.
  A GPU newer than the list runs the PTX, which needs a driver that knows CUDA 12.9 (575 or
  newer); such GPUs need newer drivers anyway. CUDA 13 would need 580 or newer and drops Pascal
  and Volta, hence 12.
- **Architectures** (`CUDA_ARCHS` in [`cuda-variant.sh`](../../scripts/release/cuda-variant.sh)):
  device code (SASS) for every supported generation, plus PTX for what comes after:

| Arch | GPUs |
| --- | --- |
| `61-real` | Pascal: GTX 10xx, P40 |
| `70-real` | Volta: V100, Titan V |
| `75-real` | Turing: RTX 20xx, GTX 16xx, T4 |
| `80-real` | Ampere datacentre: A100, A30 |
| `86-real` | Ampere: RTX 30xx, A10, A40 |
| `89-real` | Ada: RTX 40xx, L4, L40 |
| `90-real` | Hopper: H100, H200 |
| `120a-real` | Blackwell: RTX 50xx, RTX PRO 6000 |
| `90-virtual` | PTX, JIT-compiled once on GPUs newer than the list (e.g. B200) |

  llama.cpp's own default for CUDA 12.9 ships PTX for 50, 61, 70, 75, 80 and 90 and SASS only for
  86, 89, 120a and 121a. PTX from a 12.9 toolkit needs a 575+ driver and a JIT compile on first
  start, so the release ships SASS for every listed generation instead and keeps PTX for the
  future only. Blackwell must be `120a` (llama.cpp's FP4 paths need the arch-specific variant,
  which has no forward-compatible PTX), which is why the PTX is compute 9.0. Maxwell (50, 52) is
  left out: 4 GB cards on a 2014 architecture.
- **Size**: a 960 MB binary in a 565 MB archive (xz), against 36 MB and 10 MB for the CPU build.
  About 550 MB is static cuBLAS, whatever the list; each architecture adds about 50 MB of ggml
  device code (a build for `89-real` alone is 615 MB).

### Build

[`build-cuda.yml`](../../.github/workflows/build-cuda.yml) runs on release tags (a cargo-dist
`local-artifacts-jobs` entry) and on pull requests that touch `Cargo.toml`, `Cargo.lock`,
`rust-toolchain.toml`, the workflow or `scripts/release/`. It installs the CUDA compiler and
static libraries from NVIDIA's apt repository (no driver), then runs
[`scripts/release/cuda-variant.sh`](../../scripts/release/cuda-variant.sh):

- `build`: `cargo build --profile dist --locked` with cargo-dist's release features plus `cuda`,
  and `CMAKE_CUDA_ARCHITECTURES` + `CUDAARCHS` set to the list above. Both only take effect on a
  fresh CMake build dir: a stale `target/.../llama-cpp-sys-2-*/out/build` keeps its old list.
- `verify`: fails unless ggml's static library holds exactly the expected SASS and PTX, the binary
  links `libcuda.so.1` and no CUDA toolkit library, and `--version` runs (against the driver stub).
- `package`: `studio-worker-x86_64-unknown-linux-gnu-cuda.tar.xz` in cargo-dist's layout (one
  top-level directory: the binary, `CHANGELOG.md`, `LICENSE`, `README.md`) and its `.sha256`.

Measured on GitHub's `ubuntu-22.04` runner (4 vCPU): 85 minutes to compile, 2 to compress, about
95 for the whole job, which therefore sets the pace of a release (the CPU builds take about 25).
Performance, on an RTX 4090 with `qwen3.5-0.8b` loaded, for a 3,616-token prompt and 64 tokens
out: 0.28-0.33 s with this build, 13.5 s with the CPU build of the same release.

Locally, with the toolkit installed:

```bash
scripts/release/cuda-variant.sh build && scripts/release/cuda-variant.sh verify
# One architecture, much faster (use a fresh target dir or delete llama-cpp-sys-2's out/build):
export CUDA_ARCHS=89-real EXPECTED_SASS=sm_89 EXPECTED_PTX=
scripts/release/cuda-variant.sh build && scripts/release/cuda-variant.sh verify
```

### Installer

cargo-dist's shell installer knows one archive per target.
[`scripts/release/patch-installer.sh`](../../scripts/release/patch-installer.sh) teaches it the
CUDA one, in a hand-written step of `build-global-artifacts`:

- `STUDIO_WORKER_VARIANT=auto` (the default): the CUDA archive when the NVIDIA driver's
  `libcuda.so.1` is in the linker cache (`ldconfig -p`) or a usual driver path (including WSL's
  `/usr/lib/wsl/lib`), the CPU archive otherwise.
- `STUDIO_WORKER_VARIANT=cuda` / `cpu`: that archive. `cuda` without a driver warns and installs
  it anyway; `cuda` on a target without a CUDA build warns and installs the CPU one. Any other
  value is an error.
- The installer prints its choice (`variant: cuda (NVIDIA driver found; ...)`), and verifies the
  CUDA archive against its embedded sha256 like every other archive.

```bash
curl --proto '=https' --tlsv1.2 -LsSf \
  https://github.com/webbertakken/studio-worker/releases/latest/download/studio-worker-installer.sh \
  | STUDIO_WORKER_VARIANT=cpu sh
```

The PowerShell installer is unchanged: Windows has no CUDA variant.

The patch anchors on cargo-dist 0.30's generated text and fails the release when an anchor moves,
rather than ship an installer that ignores the variant.
[`test-installer.sh`](../../scripts/release/test-installer.sh) then installs every variant from the
real archives into a throwaway `HOME` before anything is published. On pull requests,
[`installer.yml`](../../.github/workflows/installer.yml) runs the same test against a freshly
generated installer and fake archives.

### Auto-update

The updater ([`src/update.rs`](../../src/update.rs)) installs the variant the running binary was
built as (`variant::Variant::current()`, from `cfg!(feature = "cuda")`), and passes it to the
installer as `STUDIO_WORKER_VARIANT`:

| Running | Release has the CUDA archive | Installs | Log (`op="variant"`) |
| --- | --- | --- | --- |
| CPU | either | CPU | info: keeping the running build variant |
| CUDA | yes | CUDA | info: keeping the running build variant |
| CUDA | no | CPU | warn: release ships no cuda build for this target |

A CUDA update also refuses an installer that does not read `STUDIO_WORKER_VARIANT` (one cargo-dist
generated without the patch): it would install the CPU build, so the update is not applied and is
retried on the next check. `studio-worker --version` and the daemon's startup banner name the
variant: `studio-worker 0.4.13 (cuda)`.

### After a cargo-dist upgrade

`release.yml` is generated, and `allow-dirty = ["ci"]` lets it carry the one step cargo-dist cannot
generate. After `dist init` or `dist generate`:

1. temporarily remove `allow-dirty` (dist refuses to regenerate with it), regenerate, restore it;
2. re-add the `studio-worker` step and its `${{ steps.studio-worker.outputs.paths }}` upload path
   to `build-global-artifacts` (git shows them as removed);
3. run `installer.yml` (it also checks the step is present) and fix any anchor `patch-installer.sh`
   reports.
