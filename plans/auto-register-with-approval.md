# Auto-register with operator approval (Option C)

End-user flow: install binary → run it → done.  No bootstrap token,
no manual studio URL, no manual form.  The worker auto-registers with
`studio.minis.gg`, the operator (Webber) sees a Pending Workers row in
the studio dashboard, clicks Approve, the worker's next poll picks up
its `worker_id` + `auth_token` and starts heartbeating.

Two repos:

- **`webbertakken/studio-worker`** (this repo) — new auto-register
  flow, polling loop, UI status states, `--label` override.
- **`minigames-rust-workers/apps/studio`** — new D1 table, new HTTP
  routes, dashboard Pending Workers panel + Approve / Reject buttons,
  rate-limiting.

## Goals (must-haves before "done")

- A fresh user runs `studio-worker ui` (or `studio-worker run`) with
  no config, and the binary:
  1. Generates a per-install fingerprint (UUIDv4 in
     `~/.config/minis-studio-worker/install-id`).
  2. POSTs `/workers/register-request` with
     `{ hostname, username, vramTotalGb, vramThresholdGb,
        supportedModels, installId, registrationSecretHash, label? }`.
     `registrationSecret` is a fresh random 32-byte token kept
     locally; only its SHA-256 hash leaves the box.
  3. Stores `{ requestId, registrationSecret }` in
     `config.toml`.
  4. Polls `/workers/register-requests/:id`
     (with the secret as the bearer) every 30s.
  5. On `approved` → writes `worker_id` + `auth_token` to
     `config.toml`, drops `registrationSecret` + `requestId`, joins
     normal heartbeat / claim loop.
  6. On `rejected` → logs reason, exits non-zero (CLI) or shows a
     Rejected state on the UI Status tab.
- Operator sees a **Pending Workers** panel in the studio dashboard
  with hostname + username + VRAM + optional label + source IP, plus
  **Approve** / **Reject** / **Reject + ban this IP** buttons.
- The shared `WORKER_BOOTSTRAP_TOKEN` path stays as a privileged
  override (`studio-worker register --bootstrap-token <T>`) for
  operator-side workers + local dev.

## Open design forks (need your call before code)

1. **Auth on the poll endpoint.**
   - (A) Worker presents the raw `registrationSecret` as a bearer
     token.  Studio compares against the stored SHA-256 hash.
     Simple, HMAC-equivalent security. **(my pick)**
   - (B) Public/private keypair generated by the worker, public key
     uploaded with the request, polls signed.  Stronger but adds
     key management.
2. **Anti-abuse rate limit on `/workers/register-request`.**
   - (A) 10 requests / hour / IP via Cloudflare's Rate Limiting API.
     Plus dedup: if the same `(sourceIp, hostname, username)` tuple
     already has a pending row, return the existing `requestId`
     instead of creating a duplicate. **(my pick)**
   - (B) Require a "registration capability token" (signed JWT, no
     expiry) baked into the binary at build time.  Cheap to revoke
     by rotating the key.  Halfway between B+C from the design chat.
3. **`--label` UX.**
   - (A) Optional flag on `studio-worker run` / `studio-worker ui`;
     also a Config-tab field set before first registration.  Stored
     in config.toml so it sticks across restarts. **(my pick)**
   - (B) Auto-derive from `$USER@$HOSTNAME`; no label field at all.
4. **Rejected behaviour.**
   - (A) Worker stops trying entirely.  CLI exits non-zero.  UI
     shows `Rejected: <reason>` permanently until the user runs
     `studio-worker register --reset` to start a fresh request.
     **(my pick)**
   - (B) Worker keeps polling forever, just in case operator
     un-rejects.
5. **Existing `worker_id` mid-flight (i.e. the deployed v0.1.2 with
   `dev-bootstrap-token` baked in as the default).**
   - (A) On upgrade, if `worker_id` + `auth_token` are populated,
     do nothing (existing workers keep working).  Only fresh
     installs hit the new flow. **(my pick)**
   - (B) Force everyone to re-register through the approval flow.
     Cleaner but breaks every existing worker.

## Studio-side changes (separate PR in `minigames-rust-workers`)

### D1 schema (new migration)

```sql
CREATE TABLE workerRegistrationRequests (
    id                        TEXT PRIMARY KEY,
    install_id                TEXT NOT NULL,
    registration_secret_hash  TEXT NOT NULL,
    hostname                  TEXT NOT NULL,
    username                  TEXT NOT NULL,
    label                     TEXT,
    vram_total_gb             REAL NOT NULL,
    vram_threshold_gb         REAL NOT NULL,
    supported_models          TEXT NOT NULL,     -- JSON
    source_ip                 TEXT NOT NULL,
    user_agent                TEXT,
    status                    TEXT NOT NULL,     -- pending / approved / rejected
    requested_at              INTEGER NOT NULL,
    decided_at                INTEGER,
    decided_by                TEXT,
    rejection_reason          TEXT,
    -- On approve, these are populated and the studioWorkers row exists:
    issued_worker_id          TEXT,
    issued_auth_token         TEXT
);

CREATE INDEX workerRegistrationRequests_install_id
    ON workerRegistrationRequests (install_id);
CREATE INDEX workerRegistrationRequests_status
    ON workerRegistrationRequests (status, requested_at);
```

### HTTP routes (new)

| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| POST   | `/workers/register-request`            | none + rate limit | Create pending row, return `{ requestId }` |
| GET    | `/workers/register-requests/:id`       | bearer = secret   | Poll status; returns `{ status, workerId?, authToken? }` |
| GET    | `/studio/workers/pending`              | studio admin      | List pending requests |
| POST   | `/studio/workers/pending/:id/approve`  | studio admin      | Mint `worker_id` + `auth_token`, mark approved |
| POST   | `/studio/workers/pending/:id/reject`   | studio admin      | Body: `{ reason }`.  Mark rejected. |

`/workers/register` (current bootstrap flow) **stays** for the
operator-bootstrap path.

### Dashboard UI

New tab in `apps/studio/src/client/modules/graphics/`:

- **Pending Workers** panel: list of pending requests with
  per-row Approve / Reject buttons + a reason field for Reject.
- Approved requests fall off the list; rejected stay with a
  "rejected" pill until cleaned up (TTL or a Clear button).

## Worker-side changes (this repo)

### Config additions

```toml
# Set on first run if no worker_id is present.  Cleared once
# approval succeeds.
[registration]
request_id          = "rr-<uuid>"
registration_secret = "<random 32-byte hex>"
install_id          = "<uuidv4>"   # stable across reinstalls if
                                    # ~/.config persists
status              = "pending"    # / "approved" / "rejected"
status_message      = ""
last_polled_at      = "2026-05-25T20:00:00Z"
```

Plus the existing `worker_id` / `auth_token` / `label?` /
`bootstrap_token?` fields stay.

## Non-goals (deferred to v1.1)

- Email / Discord notification to the operator when a new pending
  request lands.  v1: refresh the dashboard.
- "Approve all from IP X" bulk action.
- Auto-expiry of stale pending rows after N days.
- Per-user invite tokens (Option A).  v1 relies on operator
  approval and IP rate limiting; if abuse surfaces we layer
  invite tokens on top.
- Auth on poll using public-key crypto (Option B above).  v1 uses
  the registration-secret bearer.
